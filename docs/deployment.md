# Cloudflare deployment

Cloudflare Workers Builds runs CI and deploys both Astro applications. Pushes to `main`
automatically deploy the production Workers. Other branches deploy two separate staging
Workers for review before merge. GitHub hosts the repository, and the GitHub Actions CI
workflow has been removed.

All four remote build connections are configured and verified against the reference settings.
The initial working tree passed deployed staging smoke checks before Access was enabled.
Both staging Workers now require the owner's Cloudflare account login. The first Git-triggered
Cloudark build still requires these repository changes to be committed and pushed.

Both applications use asset-first delivery with Worker fallback. Each app's `_headers` file
applies the security policy to static responses. Middleware applies the same policy to Worker
responses.

## Workers and branch selection

Connect the repository separately to each Worker. Each root directory contains the app's
Wrangler file, as described in Cloudflare's [monorepo setup](https://developers.cloudflare.com/workers/ci-cd/builds/advanced-setups/#monorepos).

| Environment | Worker | Root directory | Branches | Deploy command |
| --- | --- | --- | --- | --- |
| itsvari production | `itsvari-com-website` | `apps/itsvari` | `main` only | `pnpm run deploy` |
| V4RI production | `v4ri-music` | `apps/v4ri` | `main` only | `pnpm run deploy` |
| itsvari staging | `itsvari-com-website-staging` | `apps/itsvari` | All except `main` | `pnpm run deploy:staging` |
| V4RI staging | `v4ri-music-staging` | `apps/v4ri` | All except `main` | `pnpm run deploy:staging` |

The personal production Worker keeps its existing name and `itsvari.com` attachment. The new
`v4ri-music` production Worker is reserved without code or routes; its first `main` deployment
will attach `v4ri.xyz` using the checked-in Wrangler configuration. The production configs set
`workers_dev` to `false`. Staging uses the app's `staging` Wrangler environment, enables
`workers.dev`, and has no production custom-domain routes. The old non-production version-upload
trigger on `itsvari-com-website` has been removed.

Each site has one shared staging Worker. Non-`main` branches replace the deployment on that
Worker, so check the deployed commit before accepting a staging review.

Use `pnpm run deploy` explicitly. `pnpm deploy` is pnpm's built-in workspace packaging command
and does not invoke the app's Wrangler script.

## Build settings and validation

All four connections use these settings:

| Setting | Value |
| --- | --- |
| Build command | `pnpm run build:cloudflare` |
| Build caching | Enabled |
| Included watch paths | `*` |
| Excluded watch paths | None |
| `NODE_VERSION` | `26.13.0` |
| `PNPM_VERSION` | `12.16.1` |
| `TX02_FONT_BASE_URL` | `https://media.itsvari.com/fonts/tx-02/v1/` |
| `SKIP_DEPENDENCY_INSTALL` | `true` |

Set `CLOUDFLARE_ENV=staging` on both staging connections. Leave that variable unset on the
production connections. Keep `packageManager: "pnpm@12.16.1"` consistent in the repository
and both app manifests. Cloudflare's [build image settings](https://developers.cloudflare.com/workers/ci-cd/builds/build-image/)
control tool selection and automatic dependency installation.

The app command delegates to the repository's `build:cloudflare` script. The script installs
development dependencies with `--frozen-lockfile --strict-peer-dependencies --prod=false`,
then runs full and production dependency audits, media integrity checks, lint, type checks, tests, both application
builds, and both Wrangler deployment dry-runs. The deploy command runs only after validation
succeeds. Each Worker connection runs the complete validation pipeline.

[`workers-builds-settings.json`](workers-builds-settings.json) records the intended settings.
It is a reference file, not a native Cloudflare configuration file. Apply the settings through
the dashboard or the [Workers Builds API](https://developers.cloudflare.com/workers/ci-cd/builds/api-reference/).
The API needs a user-scoped token with `Workers Builds Configuration: Edit` permission, an
authorised Cloudflare GitHub App installation, and a build token for deployment.

The installed `cf` CLI manages the build connections using its existing OAuth login. Wrangler
continues to deploy the configuration generated by Astro. To check the saved account settings:

```sh
pnpm run check:cloudflare-builds
```

This read-only command checks that each Worker has exactly one trigger, uses this repository,
and matches the reference commands, branch filters, watch paths, caching, and build variables.
It requires an authenticated `cf` CLI and is an operator check, not part of the build container.

## Free-tier build budget

Workers Free includes 3,000 build minutes per month across the account, one concurrent build,
and a 20-minute timeout per build. The Free build environment provides 2 vCPU and 8 GB of
memory. See the [current build limits](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/).
Cloudflare describes Free usage as capped at 3,000 build minutes, while additional minute
charges apply to Workers Paid. See the [pricing announcement](https://blog.cloudflare.com/full-stack-development-on-cloudflare-workers/).

A conservative planning assumption of 100 pushes per month, two Worker builds per push,
and five minutes per build uses 1,000 minutes. This is an estimate, not a measured build time.
Other Workers Builds projects on the account share the same allowance.

The account subscription check on 3 November 2026 shows no Workers Paid plan. This migration
does not change subscriptions or enable paid build resources. Existing R2 billing is already
enabled on the account. Before this migration, R2 held 1,079,550 bytes across 13 objects.
The new delivery set adds 4,037,081 bytes across 39 objects, well within the shared allowance.

## Image delivery

The `cloudark-media` R2 Standard bucket serves `https://media.itsvari.com`. It contains only
28 pre-generated press WebPs, nine event posters, and the two required TX-02 webfonts.
Original press photographs remain outside Git and the public bucket. Image variants, originals,
poster copies, QA screenshots and generated output are ignored by Git. Both applications exclude
their local `/photos/` directories from Worker static asset uploads.

Images use versioned `cloudark/v1/` keys with one-year immutable caching. No Cloudflare Images
storage or runtime transformations are enabled. The public `r2.dev` endpoint is disabled.
The content model stores delivery URLs, while the press manifest preserves responsive sizes
and dimensions. Small logos, favicons and other interface assets remain in Git.

`docs/content/media-delivery.json` records the delivered files' size, MIME type and SHA-256.
Every CI build runs `pnpm run check:media` to verify the live files, cache headers and font CORS.
To inspect a local upload plan, run `node scripts/publish-media.mjs`. Add `--publish` to upload
the 37 image files and verify them. This operator command requires local ignored delivery files
and Wrangler authentication. Use a new versioned key when an image changes; update its content
reference and integrity manifest together. Site builds reference R2 without uploading media.

## Licensed TX-02 webfonts

The owner has confirmed a web-use licence. Font binaries remain outside this public repository.
The shared `FontFaces.astro` component needs only the normal-width upright Regular 400 and
Medium 500 faces. Labels and dates use Departure Mono. Headings and italic emphasis use
Redaction, so no additional TX-02 weights, widths, or obliques are needed.

| Original file outside the repository | Hosted filename |
| --- | --- |
| `BerkeleyMono-Regular.woff2` | `tx-02-regular.woff2` |
| `BerkeleyMono-Medium.woff2` | `tx-02-medium.woff2` |

The current originals are in `/Users/vari/Downloads/TX-02_webfonts`. Together, the two WOFF2 files
are 60,184 bytes. Their delivery directory is `https://media.itsvari.com/fonts/tx-02/v1/`.
They use `font/woff2` content types and immutable caching. Bucket CORS permits the production,
staging, version-preview and local development origins that need the fonts.

`TX02_FONT_BASE_URL` is set to that directory URL in all four Workers Builds
environments. Vite reads the value while compiling the shared font component. A Worker
runtime variable alone does not configure a prerendered page. Local development can use an
ignored app `.env.local` with the same setting. The URL is public configuration and contains
no credentials.

Site builds emit only the two remote `@font-face` URLs. They do not download, copy, bundle, or
upload the font binaries. Without `TX02_FONT_BASE_URL`, builds use the monospace fallback.

Keeping fonts outside Git prevents repository redistribution. Browser delivery still requires
downloadable font URLs, and CORS does not control who can download them. The print and PDF CV
keeps its existing embedded body fallback because web-use permission does not establish PDF
embedding rights.

## Staging checks before merge

Both staging Workers have whole-Worker Cloudflare Access applications. They allow only
`contact@itsvari.com` through the Cloudflare account identity provider, with 12-hour sessions.
The policies cover all paths, static assets and current or future version URLs. There are no
bypass or service-auth rules. Production Workers remain public.

Run `pnpm run check:staging-access` to read back the policies and prove anonymous requests to
pages, static files and the currently deployed version URLs redirect to Access.

Both staging URLs are active. For content smoke checks, sign in with the owner's account and
supply each application's `CF_Authorization` cookie through `ITSVARI_SMOKE_ACCESS_TOKEN` and
`V4RI_SMOKE_ACCESS_TOKEN`. Keep those session tokens out of Git and logs. Then run:

```sh
ITSVARI_SMOKE_BASE_URL=https://itsvari-com-website-staging.itsvari.workers.dev \
V4RI_SMOKE_BASE_URL=https://v4ri-music-staging.itsvari.workers.dev \
pnpm run smoke:deployed
```

The smoke harness checks direct HTML navigation, static and Worker response security headers,
HTML 404 status and content, and the short cache policy on RSS and sitemap responses.
Review the content and run both staging checks before merging to `main`.

For a local staging build, run `pnpm run build:staging` from the app directory, followed by
`pnpm run deploy:staging`. Select the staging environment while building: changing only the
deployment command cannot correct an Astro build generated for production.

## Production deployment and rollback

Merging to `main` runs validation and automatically deploys both production Workers. The
separate staging Workers remain outside the production custom-domain routes.

Before merge, record any existing production version IDs. After deployment, check both domains:

```sh
ITSVARI_SMOKE_BASE_URL=https://itsvari.com \
V4RI_SMOKE_BASE_URL=https://v4ri.xyz \
pnpm smoke:deployed
```

If a production check fails and the Worker has a previous production version, restore that
version in the Cloudflare dashboard or with Wrangler's rollback command. The custom domain
stays attached to the Worker, so version rollback does not require DNS changes.

The first `v4ri-music` release has no earlier production version to restore. Recovery for that
initial release requires a corrected deployment from the reviewed source. Keep its staging
deployment available while checking the first production release.
